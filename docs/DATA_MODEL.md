# Firestore schema and access contract

Current contract after the Functions stage, 17 November 2026. Timestamp means Firestore Timestamp (UTC instant); event timezone is an IANA name. Nullable fields are stored explicitly as null. This is the application contract; server-only writes are validated by the emulator-only Functions in `FUNCTIONS.md`. Rules do not validate Admin SDK writes.

## Collections and fields

`about` allowed fields, each an array of option keys (never the display label — see `occupationOptions`/`heardAboutOptions`/`culturalBackgroundOptions` in `lib/participant/forms.dart` for the key→label map) except where noted:
- `ageRange`, `gender`, `accessNeed`, `loneliness`, `satisfaction`: unchanged, single string.
- `occupation` (was `currentActivity`, single string): array of `working`/`studying`/`looking_for_work`/`retired`/`prefer_not_to_say`; `prefer_not_to_say` is exclusive with every other value.
- `heardAbout` (was `referral`, single string): array of `friend`/`uni_campus`/`social_media`/`local_club`/`other`; no exclusivity.
- `heardAboutOther` (was `referralOther`): required non-empty (≤200 chars) exactly when `heardAbout` contains `other`; empty otherwise.
- `culturalBackground` (was a single string): array of `aboriginal_torres_strait_islander`/`born_outside_australia`/`neither`/`prefer_not_to_say`; `neither` and `prefer_not_to_say` are each exclusive with every other value, including each other.

A profile written before this change has these as old-shaped single strings. There is no backend migration script — `lib/participant/forms.dart`'s `migrateAbout()` is a pure function applied every time a profile is loaded for editing, converting the old shape to the new one by reverse-mapping the stored display-label string back to its option key. The next save writes the new shape; nothing is migrated at rest until then. Missing answers stay missing; seed does not invent demographic answers.

## Storage

Not enabled on `rally4ever-3adaf` yet; `storage.rules` is written and reviewed but **not deployed**. Only one path is in use: `profilePhotos/{uid}/avatar.jpg` — a single square JPEG, resized client-side to 512×512 and capped at 5 MB before upload. Owner-only write/delete (validated by `storage.rules`: JPEG content type, ≤5 MB); read is any signed-in verified user (same visibility as a participant's first name elsewhere in the app). `users/{uid}.photoUpdatedAt` is the existence/cache-busting marker — null/absent means no photo, initials are shown instead. Removal by a coach/admin (`functions/src/admin_roles.ts`'s `removeParticipantPhoto`) goes through the Admin SDK, which bypasses `storage.rules` entirely, and is audited in `profilePhotoAudits`.

Correction entry: `at`, `by`, `reason`, `previousStatus`, `newStatus`; retain `scannedAt`, method, location and original scan. Confirmation/rejection are server-authorized transitions; no client can forge either confirmations or corrections. Functions tests verify reason enforcement and scan preservation.

## Identity and roles

Normalize emails identically in Dart and server scripts with trim/lowercase; use the normalized address as the mapping document ID, as requested for the Functions stage. Functions validate addresses and reject slash-containing inputs. Firebase Auth UID is canonical, never a coach-local profile ID. A verified Auth user must also have an active trusted profile. `mergedInto != null` blocks app access for the old UID. For coach access, an admin-issued Auth role/roles claim is mandatory; the protected profile mirror can only restrict it, and coachEnabled=false blocks access immediately. A domain or coach profile field alone grants nothing. Participant access remains available to dual-role users. This permits immediate field-based demotion even when an old token has elevated claims. Unknown roles have no privileged access. Clients cannot assign role fields or Auth claims.

The Functions stage adds account provisioning, concurrent normalized-email reservation, coach lookup/create, dry-run/apply merges and attendance callables. Emulator tests exercise two-coach creation of the same email and verify one canonical Auth UID/profile. The old backend duplicate defect remains unverified; no legacy-data fix is claimed. A merged old Auth account is not silently granted a token for the target account: registerIdentity returns requiresSignIn=true. Auth credential/provider consolidation is not implemented.

Admin access covers listed business collections, with explicit exceptions for secrets and attendance writes. Unknown paths remain denied to everyone. This intentionally routes admin attendance changes through audited server operations too.

## Queries and indexes

Use `status == published` for participant event queries, `coachUids array-contains uid` for coach events, `uid == currentUid` for personal RSVPs/attendance/notifications, and `eventId == assignedEventId` for coach rosters. Rules are not filters: unscoped collection reads by participants/coaches are denied. Attendance lookup uses a scoped query so an absent attendance record returns an empty result rather than attempting to authorize nonexistent document fields.

Composite indexes are listed in `firestore.indexes.json` for event discovery, coach events, personal intent/attendance, coach attendance queues, feedback selection, inbox and event feedback. Equality-only attendance lookup uses default index merging. Local rule tests do not prove that production composite indexes have been deployed; there is no deployment in this stage.

## Verification boundaries

Rule tests cover read/write denials and permitted paths with mocked claims; Auth integration tests log in to the real local Auth emulator and read through Firestore rules. Dart tests cover role precedence, normalization, separate intent/attendance states, event times and emulator fail-closed guards. Flutter SDK services are not yet wired to UI, and Android/iOS/web runtime integration is not claimed. No Storage collection/service is needed for this stage. `emulatorPushes/{notificationId}` is a private server-only test-delivery collection with notificationId, uid, eventId, type, route, tokenCount and recordedAt; all client access is denied by the default rule. Moved merge references have mergedFromUid provenance; originals are archived in mergeAudits.

References used: [Firebase rules unit testing](https://firebase.google.com/docs/rules/unit-tests), [Auth emulator integration](https://firebase.google.com/docs/emulator-suite/connect_auth). These distinguish mocked rule contexts from actual emulator authentication; Admin SDK access bypasses rules.


Latest additional collections: `rateLimits/{scope_hash}` (count, resetAt); `noAppRequests/{requestId}` (email, safe request data, secretHash, createdAt, expiresAt, consumed, verifiedAt); `roleChanges/{uid}` (operationId, status, expiresAt). These are server-only. `roleAudits/{id}` is admin-readable/server-written and records actorUid, targetUid or eventId/coachUids, action, reason, enabled, createdAt, appliedAt and status. No participant may alter any role metadata. Check-ins/coach notifications now include identityVerification; coach notifications also retain scannedAt/distanceM review evidence.
